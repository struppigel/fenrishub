Fenris

Fenris is the name for the FRST log analyzer that I initially created for myself as a commandline tool and eventually turned into a web application for shared usage. It is currently on malwareanalysis.cc and also serves as upload platform for logs.

Uploads

This view lists all uploaded logs. Per default you see only the ones assigned to you ("my channel"). Use the channel dropdown to switch between "my channel", "all channels" (every log), "unassigned" (the general channel), or a specific helper's channel. Logs have a unique ID consisting of two keywords and potentially a suffix. Logs are automatically categorized into FRST, Addition, FRST&Addition, Fixlog, Unknown. Depending on that category their keywords have a different color. Use the log type dropdown to show only logs of one category, or "all log types" (the default) to show every category.

The keywords are shown to the user after upload and will allow you to find them properly. There is a search bar on the top, where you can type the keyword or username and press enter, such that it will filter logs that way. A clear link appears whenever a search, user, or channel filter is active and resets all filters back to the default view.

The copy upload url button gives you the URL to share when instructing users to upload. It offers two options: my channel copies your helper URL, so their uploads are assigned to you, while general channel copies the generic upload URL, so their uploads stay unassigned.

Pro-tip: If you add ?u=User123, you can prefill the username for the uploader, e.g.: https://malwareanalysis.cc/upload/struppigel/?u=User123. If you don't want to assign uploaded logs to you, e.g., provide generic instructions, use this generic upload page: https://malwareanalysis.cc/upload/.
Tip: Users often copy the very first FRST scan instructions, so using the general upload page for the first comment makes sense, such that these logs are unassigned.

The buttons merge and mergalyze will:

  • create one log out of the selected ones
  • move the old, still separate logs into trash with -trsh suffix - that means in case you merged the wrong logs, you can still get the old ones back
  • mergalyze will additionally open the merged log in the analyzer whereas merge stays on the uploads page

The diff button shows a differential of two selected logs.

The delete button moves logs to trash. The trash deletes logs after 7 days automatically (Note: All logs are deleted after 30 days since upload time automatically for privacy reasons and to keep the database small).

The rescan button triggers a new log analysis for selected logs and updates the statistics. This is useful if you changed rules (more about that later in rules).

For each log the following data is shown:

keywords (assignee) filename | username | upload-timestamp | log type | md5 hash total line counter | log analysis verdict counts | percentage of known lines

The md5 hash is there to see if there are duplicates. If a log has a duplicate, it will mark the md5 hash of both logs yellow-ish, such as in the picture above.

For each individual log you also have an assign or unassign button, a view button, analyze and delete.

view shows a bit more metadata and the log contents. You can also change the name of the user that uploaded the log (sometimes users add typos or use the wrong name).

analyze is for log analysis and creating fixlists. More on that later.

delete does the same as the bulk delete button: It moves the log to the trash.

assign assigns the log to you as helper. The assignment prevents other helpers from deleting your log, prevents them from assigning it themselves, and makes the log directly visible in your uploads overview (in the "mine" channel) for easier access. It has otherwise no technical implications.

unassign just removes the assignment again. This is useful if you want another helper to take the log for analysis. If a log is assigned to another helper and you desperately still want to work on it but the helper isn't online and can't unassign the log, then you can copy the assigned log.

The copy button only appears if the log is assigned to someone else. The copy button creates a copy with new keywords (because these must be unique) and autoassigns the log to you.

Analyze

This is the heart of the log analysis and Fixlist creation and the original purpose of Fenris. On the left side you see the log. Each line will be categorized into one of 10 verdicts, which have their own color. The legend on the bottom explains the colors and the shorthand for each verdict category. If you click on the legend, the log lines will be filtered to show or not show lines of that category.

Log line verdicts

Bad or Malware - these are bad log lines, usually malware entries, which always must be handled in some way.

PUP - stands for potentially unwanted. That includes questionable software, the presence of legitimate remote access tools, which can either be used by the user or part of an infection, or just indicators for an infection, e.g. currently we mark the RenPy folder as PUP, although it is a legitimate execution environment but helps to identify RenLoader infections. PUP is always a case-by-case decision or user's choice.

Clean - these lines are legitimate entries in the log.

Alert - these lines create Alerts, which you will see above the log with a description if they trigger. Alerts help us identify general issues in the log that we need to address, e.g. a dying hard disk or multiple enabled antivirus products.

Warning - these are usually lines where FRST issues a warning, most of the time they need to be addressed.

Grayware - these are lines that detect illegal software such as cheats, cracks, hacktools. They pose a security risk. How you treat them, whether you demand removal or warn the user, is up to you.

Security - these mark security software such as antivirus scanners. They are a separate category from Clean so that you can get a better overview on the scanners that were already used to clean the system.

Info - these are lines that belong to the structure of FRST logs such as titles, explanations and separator lines. A line in that category cannot be moved to the Fixlog by clicking because that wouldn't make sense.

Junk - these are orphaned registry entries, temp files or junk files. Lines in that category are optional to remove, but usually added in fixlists.

? - unknown, these lines have no known category.

The analyzer has two sides: the left side is the log and the right side are the fixlist and response text you are working on.

Left side in analyzer - the analyzed log

The left side colors each log line with one of the verdicts (B, P, C, A, J, G, S, I, J, ?). The symbol at the start of the line also displays the verdict and is at the same time a button that lets you pick a verdict. The picker looks as follows.

If you change a verdict, it will be effective for the current log. If you want to persist the verdict for future logs, you should press the "save rules" button on the top. This will trigger a wizard for rule saving that lets you decide how to handle conflicts. If you are unsure what to choose in case of a conflict, most of the time "keep both rules" is the right choice. Rules that are added this way will always be either of type "parsed" or "exact line" - these types will be explained in detail in the rules section.

If there is a PUP, Malware or Warning verdict for a line with a timestamp, other timestamps that are roughly at the same time (+/- 10 minutes) or dates that are at the same day will be highlighted. That makes it easier for you to find related lines to problematic entries. The color of the highlight matches the verdict color.

When you hover over a log line, two small icons appear on the right. The copy icon ⎘ opens a menu to copy the whole line or an individual component (file path, file name, arguments, name, company, clsid, for installed programs the full uninstall registry key and the key name, or any URL/domain/IP address found in the line) to the clipboard. Right next to it, the magnifying glass ⌕ opens the same list of components, but clicking one runs a Google search for that value in a new tab - handy for quickly looking up a suspicious file path, file name or company without retyping it.

The top row has some more special buttons.

Firstly there is the edit log button, which allows you to change the log contents or paste an entire log. While in editing mode, this button will change to a parse lines button which triggers the analysis.

Next to that is a question mark ? button. If active, you can click on log lines and it will open a window with detailed information about them, especially how they are parsed, which components they have, and which rule decided about the verdict. Toggle the button again to exit the question mark mode.

Next to that is the C button. It's a quicker way to mark lines as Clean. If active, any lines that you click will receive the Clean verdict. You need to toggle the button again to exit the C mode.

The logs button hides or displays the log picker. You can use the log picker to choose and load a different log. It only shows logs assigned to you.

The FRST path button copies the path for FRST64.exe to the clipboard.

The top buttons on the right side are for the fixlist and response creation.

Right side in analyzer - fixlist and response editing

To add a line to the fixlist in progress, simply click the line on the left side. This will copy the line to the right side at the current position of the cursor. There are also ways to move many lines at once.

The B, P, J and ! buttons here will bulk move lines marked with this category to the Fixlist.

ignore FW decides if the bulk move includes the Firewall entries or not. E.g., if you reset the Firewall of the system anyway, you may decide to move all Junk entries except the Firewall.

hide fix hides the right side text area with the Fixlist to allow using more screen space while analyzing the log.

snippets lets you choose a code snippet that you may want to include in the fixlist. This is probably empty at the beginning. The snippets can be managed in the snippets view.

response lets you choose a canned speech that you may want to include for your response. This is probably empty at the beginning. The speeches can be managed in the speeches view.

save will do two things:

  1. Ask you if you want to save rules, if you changed line verdicts
  2. Save the fixlist and response and take you to its page

Both right hand panels are saved together: the fixlist and the response are saved together under fixes. On the fixes page you can then adjust the username, and edit either of the two in their tabs.

The fixlist area is prefilled with a template. You can change this template in your profile settings. The response area starts empty.

Fixes

The fixes entry in the menu opens the fixlist and response overview. It shows all fixes that you created. Other people can only see fixlists if they have the share link or token and if the fixlist is public. The token is a unique identifier for the fix.

From the overview page you can hide individual fixlists, copy their link or delete them.

If you are viewing an individual fix, you can also access the source log the list was based on (the source log is only available if the fixlist was created via the analyzer on an already uploaded log, otherwise there is no log attached).

Right next to view source log there is a reanalyze & edit link. It reopens the fixlist in the analyzer with the source log loaded on the left and the fixlist is loaded on the right, so you can re-classify lines, use the verdict picker, add snippets, and so on. When you save from there, it updates the same fix instead of creating a new one, keeping its share link, token, username and internal note intact. The stored response is loaded into the response panel too and re-saved with it. This link only appears when the fix has an attached source log.

You can change the username from here.

The fix page has two tabs: fixlist holds the fix itself and response holds the reply you write back to the user. One save writes both. The response never appears on the share page, so the person you are helping only ever sees the fixlist. Other helpers can read responses on the case timeline, if you share the link to it.

The copy buttons at the top follow the currently open tab. On the fixlist tab you get copy fix message, on the response tab you get copy response, which puts the whole reply into your clipboard.

You can edit the contents, even after sharing the fixlist link. So last minute changes are no problem. For small tweaks the text boxes on this page are enough; use reanalyze & edit when you want the analyzer's full toolset against the original log.

copy fix message will put a predefined message into the clipboard that instructs users how to fix. To change this predefined message template, click on your username on the top right, click on profile settings, and adjust the frst fix message. This frst fix message template has placeholders for the username, helpername (you), fixlist link and frst path, which will be automatically filled into the template. Some of these only work if the fixlist has an associated uploaded log, e.g., the FRST path is part of the FRST log and not the Fixlist. So if that is missing, it's probably because your Fixlist was created without a log.

The same fix message is also listed as the FRST fix speech on the speeches page. It is one entry shown in two places: editing it in the profile or on the speeches page changes both, and you can insert it into a response in the analyzer like any other speech. It cannot be deleted. Every new account starts with the default text.

Snippets

This manages your code snippets that you may want to include into fixes. Snippets can also be shared with other users.

Use add snippet to create a new snippet.

Every snippet has a category, that you can choose yourself for better organization and filtering. The default is generic.

The name of the snippet is the title that you see when you choose it. I usually name it like so: {tool or main command} {what it does} - e.g. "defender delete history", "hitmanpro scan".

A shared snippet is visible to other helpers. Non-shared snippets are only visible to you and can be used for work in progress snippets or simply things you are not willing to share.

Once you created a snippet, you need to click the select button so that it becomes available in the snippet picker in the Analyze view. To include other helper's snippets, choose the helper's name in the combobox that says "my snippets". Then press select for the snippets you want to include.

hide preview lets you see a more concise snippet list. Per default the preview shows the first two lines of the snippet code.

Suggested snippets

Snippets are suggested the same way as speeches. On the add or edit snippet page, suggest in the analyzer when names the rule tags the snippet fits; the tag editor sets the same link from the other side. After every analysis, the snippets whose tags were found in the log are listed under suggested at the top of the snippets picker, which then reads for example snippets (2 suggested), and each warning box lists the snippets for its own tags. Built-in tags work here too, so a snippet can come up for one of the analyzer's built-in warnings.

A snippet goes into whichever right panel is showing. It stops being suggested once all of its lines are in that panel, and comes back when you delete them: a snippet already in the fixlist is still suggested while you write the response, and the other way round. Clicking a log line still adds the line to the fixlist; it never adds a snippet.

When a tag is found but none of your selected snippets is linked to it, the analyzer suggests the snippets other helpers shared for that tag, under from other helpers.

Speeches

Speeches are to your written reply what snippets are to your fixlist: reusable blocks of text that you paste into the response you write back to the user. Think greetings, instructions for running a tool, or the all-clear at the end of a case.

The page works exactly like Snippets - add speech creates one, every speech has a category (default generic), speeches can be shared with other helpers, and hide preview gives you a more concise list.

As with snippets, click select so a speech becomes available in the analyzer. To use another helper's speeches, pick their name in the combobox that says "my speeches" and select the ones you want.

In the Analyze view, switch the right panel from fixlist to response using the tabs above it. The bulk add B P J ! buttons are replaced by a speeches picker, since those verdicts have nothing to add to prose. Pick a speech and it is inserted at your cursor. The snippets picker stays available in both panels.

When you press save, the response is stored on the fixlist next to its contents, so it follows you to any machine and comes back when you reopen the fixlist or use reanalyze & edit. Until then it is part of the analyzer draft in your browser, which survives a reload or an accidentally closed tab and is offered back to you together with the fixlist.

Turning part of a reply into a speech

The best speeches are usually written in the middle of a real case. When you have typed a paragraph you know you will want again, mark it in the response panel and press +speech, the button next to the speeches picker. It stays greyed out until something is marked. A dialog opens asking for a name and a category (existing categories are offered as you type, and the default is generic). You can edit the text before saving. share with other helpers is ticked by default, so untick it if the speech should stay private to you.

The new speech is saved and selected for the analyzer straight away, so it shows up in the speeches picker without reloading the page.

The dialog also offers replace names and links with placeholders. With it ticked, your own username, the forum username of the loaded log and the upload links are swapped for their placeholders before the speech is stored, which is what makes the captured text reusable on the next case rather than a souvenir of this one. See Placeholders in speeches for the tokens involved. {COUNTER} is deliberately left out of this: a number you wrote is far more likely to be a real number than a step counter, so digits are never touched.

Placeholders in speeches

A speech can contain placeholders that are filled in at the moment you insert it. The speech itself always keeps the raw placeholder, so you can reuse it for the next case.

  • {HELPERNAME} - your own username.
  • {USERNAME} - the forum username of the log currently loaded in the analyzer.
  • {UPLOADLINK_HELPER} - an upload link to your own channel, so the next log the user sends lands assigned to you.
  • {UPLOADLINK_GENERAL} - an upload link to the general channel, for when any helper may pick the log up.
  • {UPLOADLINK_HELPER_PREFILLED} and {UPLOADLINK_GENERAL_PREFILLED} - the same two links with ?u= appended, which fills the forum username in on the upload form so the user does not have to type it.
  • {COUNTER} - the next step number.
  • {FIXLISTLINK} - the share link of the fixlist the response belongs to.
  • {FRSTPATH} - the folder FRST was run from, read from the fixlist's source log.

{FIXLISTLINK} and {FRSTPATH} have no value while you write, because the fixlist does not exist yet. They stay in the response as they are and are filled in when you save the fixlist. Saving also fills a {USERNAME} or {HELPERNAME} that was left over because no log was loaded when you inserted the speech.

Everything that needs the forum user - {USERNAME} and the two _PREFILLED links - requires a loaded log. Without one, those placeholders are deliberately left in the text rather than filled with nothing, so you can see at a glance that they still need attention.

{COUNTER} counts across the whole reply rather than restarting for each speech, so you can build one numbered instruction list out of several speeches. A speech containing three {COUNTER} lines inserted into an empty response gives you 1, 2, 3; insert a second speech after it and its first {COUNTER} is 4. The count starts over at 1 whenever you insert into an empty response, so clearing the response is how you begin a fresh reply.

Suggested speeches

A speech can name the rule tags it fits, under suggest in the analyzer when on the speeches page, or from the other side in the tag editor. After every analysis, the speeches whose tags were found in the log are listed under suggested at the top of the speeches picker, which then reads for example speeches (2 suggested). The picker is shown while the right panel is on response. Only speeches you selected for the analyzer can be suggested, and nothing is inserted on its own - you still pick.

Log warnings work through tags too. An alert rule is a rule, so tag it and its speeches come up when it fires. The analyzer's built-in warnings (incomplete logs, low memory, multiple enabled AVs, recent system restore, recent Windows install) each have a built-in tag that is found when the warning is raised. You can also put a built-in tag on your own rules, for example on extra alert rules for the same problem. A warning box also lists the speeches suggested for it; click one to insert it into the response.

Tagged log lines show their tags as small chips after the line, alphabetically; a line with more than three tags shows the first three and a +N chip for the rest. Hover a line to read all its tags with their descriptions. With the right panel on response, clicking a tagged line adds its speech to the response instead of adding the line to the fixlist: directly when one speech fits, from a small menu when several do. The menu names the line's tags each speech fits and offers insert all at the top. A line without a fitting speech only shows a short note. A speech that is already in the response is not suggested again; once you delete its text, it comes back.

When a tag is found but none of your selected speeches is linked to it, the analyzer suggests the speeches other helpers shared for that tag, under from other helpers. Inserting one does not select it for you; do that on the speeches page if you want to keep it.

Rules

Rules decide about the verdict of a log line. Rules are probably the most complicated part of Fenris. You don't need the rules as a beginner, you can choose to never use this view. But if you ever want more flexibility when adjusting how log lines are parsed, this is a way to do it.

Rule sets (shared vs private)

Each user picks a rule set in profile settings that decides which rules are applied to logs assigned to them, and whether their own rules contribute to the global pool. There are two modes:

  • shared (default) - your rules are part of the global rule set used by every other "shared" user. Logs assigned to you are analyzed against that combined pool.
  • private - only your own rules apply to logs assigned to you. Your rules are also excluded from the global shared pool, so they won't affect anyone else's analyses.

Unassigned logs (general upload channel) always use the shared rule set. When a log gets assigned to you, it's re-analyzed against your effective rule set, and the counts in the uploads list switch to your view. The statistics page always reflects the shared rule set, regardless of who an upload is assigned to.

The rules list itself shows all rules from all users regardless of mode - private just means "don't include my rules in the shared pool and don't apply other people's rules to my logs."

After switching modes, cached analyses are dropped and re-computed the next time you open the analyzer for a log. You may briefly see a "refreshing analysis..." status while it rebuilds.

Rule components

Let's take a look at the add rule dialog first. A rule consists of the following components:

status decides about the verdict of a line.

match type tells how to interpret the pattern, more on that later.

priority is the priority level. I suggest using the one that fits the match type unless there are issues you cannot solve otherwise. More about priorities later.

match line / pattern - the pattern that needs to match, e.g., this might be a regex, substring or a full log line.

The description shows up as explanation if you hover over a matched line. The description is very important for Alert rules because it contains the Alert text. It is recommended to add a description for PUP too because these require a case-by-case decision.

Rule priorities

A line can have only one verdict, but several rules may match on one line. If that happens, the analyzer has to decide which rule comes first to form a verdict based on it. The rule with the highest priority will win in that case. But what happens if there are two or more matching rules with the same priority? In that case, the analyzer chooses the verdict based on verdict precedence, which is the same order as the legend in the analyzer: B < P < C < A < ! < G < S < I < J < ?

The colors in the log analyzer work a bit differently: every matching rule colors the line, not only the one that decides the verdict. Think of it as painting in layers. The rule with the lowest priority paints first and the rule with the highest priority paints last, on top of everything else. Most rules paint the whole line. Substring and file path rules paint only the text they matched, unless they have "color the whole line" ticked. So a line can show a red substring on top of a yellow line from a lower priority rule. The status badge at the start of the line always shows the verdict. If a line is only partially colored in its verdict, you can still pick that same verdict in the status picker to queue a full rule for the whole line. Picking it again removes the queued rule.

Match types

The following match types are possible:

Exact line - the line must be exactly the same as the pattern from start to end.

Substring - the line must have a matching substring. The log analyzer colors only the matched text, unless the rule has "color the whole line" ticked.

Regex - the line must match the regex. I recommend https://regex101.com/ for writing and testing regex. Change the flavor on regex101 to Python. If you want case insensitive patterns, prepend (?i) to the regex.

File path - the line is a file path. The path will be normalized, e.g., drive letter, username, Firefox profile, and Chromium-based browser profile (Chrome/Edge/Brave User Data\Default, Profile 1, ...) are internally substituted for path comparisons that make sense. This is the main difference to Substring, where these normalizations would not happen. The log analyzer colors only the file path, unless the rule has "color the whole line" ticked.

Parsed - Fenris automatically parses known log lines into components like file path, timestamp, company, name, clsid. When comparing parsed lines these lines must match for these components except the timestamp. Furthermore, file paths are extracted from parsed entries and matched by the analyzer with lowest priority (with hardcoded exceptions for execution environments like cmd, powershell).

Testing rules

In the add rule page, there is a big box named test log lines; that is where you put lines from logs inside to test if they are detected by your rule.

The result will be shown on the bottom once you added a pattern. (The example below is nonsense here, it's just for demonstration.)

Rule tags

A rule tag groups related rules - a malware family such as RenPyLoader, a source such as chrome-mal-ids, a vendor - whatever their status. Tags are shared, and any helper can create and edit them. Their main use is suggesting speeches and snippets: one speech or snippet per tag instead of one per rule.

Tags are managed on the rule tags page in the menu under your username. The page lists 12 tags at a time; search their names and notes, or narrow the list to one category or to unused tags, tags without speech or without rules. new tag and edit open the tag editor. It starts simple: a name, a regex, a description for analysts and apply automatically. The regex is searched ignoring case in the rule's description and its source line, URLs included. A new tag applies itself automatically unless you untick it.

more options holds further conditions, suggest these speeches and suggest these snippets; it opens by itself for a tag that uses those conditions, and its button says how many speeches and snippets are linked. Every condition you set must hold; leave one empty to ignore it:

  • look in - where the regex and the exclude regex look: the description, the source line, or anywhere (the default).
  • exclude regex - rules where this matches, in the same place, are left out. For example "installed software, but not microsoft".
  • rule status - the rule's own status, any of the ticked ones.
  • parsed entry type - the rule's parsed entry type, such as installed software or browser extension. Substring rules without a parsed entry, like the malext.io extension IDs, have none.

A tag with no regex, status or entry type matches nothing; you add it to rules by hand. For "OR", make two tags and pick both on the speech. Example: an uninstall speech fits a PUP on an installed program, not malware on one. So a tag "installed PUP program" with status P and entry type installed software, no regex, picked on the uninstall speech, brings the speech up only for PUP programs.

In the tag editor:

  • The preview below the buttons updates as you type the regex or change a condition, like test log lines on the rule page. It lists the rules already tagged, the tagged rules that no longer match, and the new matches. Untick false positives, then save & apply to ticked rules.
  • remove tag from all, next to the rules that no longer match, takes the tag off all of them at once. Saving the tag also asks whether to do that whenever there are such rules, for example after you narrowed its conditions.
  • apply automatically to new rules makes the tag add itself to every new rule that meets the conditions, and to a rule whose description, source line, status or entry type is edited to meet them. When you save the tag with this on, you are asked whether to also tag the existing rules that meet the conditions; with save & apply to ticked rules the ticks decide instead. Removing such a tag from a rule by hand sticks as long as those fields stay the same.
  • suggest these speeches links speeches to the tag - your own and any you selected for the analyzer, shared ones by other helpers included. Find them by name or category. A link belongs to the speech, so linking another helper's shared speech suggests it for this tag for everyone who uses it. For your own speeches, the same link can be set from the speech's form on the speeches page.
  • suggest these snippets does the same for snippets. For your own snippets, the link can also be set on the add or edit snippet page.
  • The tag list shows each tag's conditions, how many rules meet them but lack the tag as pending, and how many tagged rules no longer meet them.

On the add and edit rule pages and in the analyzer's rule review, the tags field takes existing tags only; new tags are made in the tag editor. Tags whose conditions the rule meets are suggested under the field, and tags that apply automatically are already filled in. What the field holds when you save is what the rule gets, so removing a filled-in tag leaves it off. Regexes must be simple enough for the fast regex engine: no lookarounds or backreferences, and nothing that is slow on long input. A regex that matches empty text is refused, because it would match every rule.

Categories give tags a color. Open categories on the rule tags page to add one with a name and a color, rename or recolor it, or delete it. Every tag has a category: new tags start in the default category, which can be renamed and recolored but not deleted. Pick a tag's category in the tag editor, right under its name. Every badge of the tag then shows its category's color, on the rules list, the uploads list, log search, the speeches page, the tag pickers and in the analyzer. Deleting a category moves its tags to the default category.

Rules get tags on the add and edit rule pages, in the analyzer's rule review before saving, or in bulk from the tag editor. Click a tag on the rules list to see all its rules. Built-in tags are marked as such in the list. They work like any other tag, except that they are also found when their warning is raised and cannot be deleted.

In the analyzer, the tags of the analyzed log are shown as badges in a second row of the status legend, with the number of lines they cover. Hover a tag to read its notes; click it to show only its lines, and again to show all. At the end of the row, tagged shows only the lines with any tag, and with speech only the lines that have a speech to add (yours, or one shared by other helpers). The notes are edited in the tag editor. Hovering a line shows its tags first in the tooltip, and the ? inspector lists the tags of every matching rule, including shadowed ones. A tag only reaches a line through the rules that decide its verdict: if a B rule and a P rule match the same line and the line ends up B, the P rule's tags do not count for it.

The stats page charts how many analyzed logs contain each tag, per day, week or month, and lists every tag found in the range with its share of the analyzed logs. It reads the shared analysis, like the rest of that page, and a rule tagged later counts for older logs too. By default the chart draws the 10 most found tags, leaving out categories of priority 0; pick a category (for example a family category) to see only its tags, or pick tags to draw exactly those. Click a tag in the table to search the logs that have it.

Cases

The cases view is pretty much still work in progress, so a little wonky, but already usable. The idea is that you see all logs and fixlists for one case at once and can add your own notes about the removal process, e.g., for steps to do later, to not forget things.

Creating cases

If you are learning or observing other helpers, please stick with the training/observer option.

The username should be the exact name that is saved in Fenris as the log's username.

In the symptom description I typically copy/paste the initial text or help request of the user.

The reference URL is, e.g., a link to the forum post with the help request.

auto-assign will assign newly uploaded logs by that user to you if they were uploaded into the general upload channel. This makes only sense if you are actually working on the case. You should of course not snatch other helper's posts by auto-assigning them. That's why the training/observer case cannot auto-assign.

After you created a case, the view will look relatively empty.

But if you chose the right username and the user uploaded logs to Fenris, you can press add all items for u/username and this will automatically add all logs of this user to the case. Alternatively you can choose every log separately.

This is how an actual case looks like after adding logs and fixlists. In an actual case (not training) new user logs will automatically appear in the case. The entries in the case view are sorted by upload or creation time.

A Response entry shows the full reply you wrote, so you can read back what you told the user without leaving the case. The small copy button copies the whole response, and the title links to the fixlist on its response tab. It is titled with the same token as its fixlist so the two are easy to match up, but that token belongs to the fixlist: a response is never shared and has no link of its own.

A response is its own item in the case, just like a log or a fixlist. It is added and removed on its own, it sorts by when you wrote it rather than sitting next to its fixlist, and you can pin notes to it with +. Unlinking a fixlist leaves its response in the case, and unlinking a response leaves the fixlist.

The case view also supports adding notes, which I generally use to remind me of things I should still do.

A note is always attached to a log, fixlist or another note. To add a note, press the little + button.

You may have noticed that some parts of the case view are on the left and others on the right. This mimics common messenger layout like Whatsapp. The logs that the user uploaded are on the left. Your own creations like Metadata, Fixlists and notes are on the right.

The case view also shows log lines statistics, which makes it possible to see how log lines for B, P, ! disappear over time due to your fixes and which ones are left and must be addressed.

Trashed logs do not appear in case view. So if you trash a log, it will be removed here as well.

Pressing the small red x button will detach an uploaded log reference from the case view. It does not delete logs or fixlists. It does however delete notes since these are only available in cases. Metadata cannot be deleted from here, only if you delete the whole case.

To prevent cases from auto-assigning logs or just to mark them as done for yourself, press the small pencil on the META entry. Then change the status to closed.

Merging logs from inside a case

Each log row in a case has a checkbox on the left of the type badge. Tick two or more of them and press the merge button in the top action bar to combine the selected logs into a single merged log. The sources are moved to trash, the first selection's upload id is retained, and the merged log is linked to the case automatically. This works the same way as the merge button in the uploads view, but limited to the logs that are already part of this case.

If the selected logs belong to different forum usernames, you'll be asked which username to use for the merged log before the merge runs.

Opening a log in the analyzer

Each log entry now has a small magnifying glass icon next to the action buttons. Clicking it opens that log in the analyzer in a single step, so you don't have to leave the case view and locate the log in the uploads list first.

Sharing a case with other helpers

Any logged-in helper holding the link to a case can open it in read-only mode - just copy the URL from the address bar and send it. They will see the timeline, notes, metadata and stats, but cannot add notes, merge, unlink, edit metadata, or delete. A small "view-only - owned by <owner>" hint appears in the top bar for shared viewers. Only the case owner can mutate the case.
